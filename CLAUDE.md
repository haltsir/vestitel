# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Vestitel is a menu-bar-only macOS RSS reader (SwiftUI `MenuBarExtra`, no Dock icon, no main window). Built with SwiftPM + Command Line Tools only — there is no Xcode project and `xcodebuild` is not available. No external dependencies; no test target.

## Commands

```sh
make app    # swift build -c release + package Vestitel.app (ad-hoc signed)
make run    # make app + open Vestitel.app
make icon   # regenerate Resources/AppIcon.icns from Tools/make-icon.swift
swift build # debug build, fastest way to check for compile errors
```

The dev loop for verifying a change in the running app:

```sh
make app && pkill -f Vestitel.app/Contents/MacOS/Vestitel; sleep 1; open Vestitel.app
```

App state lives in `~/Library/Application Support/Vestitel/state.json`. Seeding or editing this file (while the app is quit) is the established way to set up test scenarios; deleting it resets the app. Setting `articles: []` and `seen: {}` while keeping `feeds` forces a full re-ingest on next launch (used to trigger the new-articles animation and re-parse with new fields).

For live tests that must not touch real data, launch a second instance with `VESTITEL_STATE_DIR=<dir> Vestitel.app/Contents/MacOS/Vestitel` — it gets its own state.json (seedable, e.g. with a feed served by `python3 -m http.server`) while the user's instance keeps running. `VESTITEL_STORE_SCAN_URL=<url>` likewise points the latest-additions scan at a stand-in listing, so the multi-page crawl can be exercised without hitting ozone.bg (the stand-in must honour `?p=N` and carry a `class="last" href="…?p=N"` pager link). Do NOT try `HOME=<dir>` for this: FileManager ignores it and the second instance will silently share and fight over the real state file. Address the test instance in AX by pid (`first application process whose unix id is <pid>`) since both processes are named Vestitel.

UI verification is done by screenshotting the popover: open it via
`osascript -e 'tell application "System Events" to tell process "Vestitel" to click menu bar item 1 of menu bar 2'`
(this *toggles* — check `count of windows` first), read the window bounds via System Events, then `screencapture -x -R "x,y,w,h"`. All content sits under `group 1 of window 1`; the tab picker is `radio group 1` (Inbox=1 … Settings=5; when a store-watch feed exists a Store tab appears at index 2 and Settings becomes 6). Do NOT set text field values via AX (`set value of text field …`) — it bypasses SwiftUI bindings and buttons stay disabled; synthesize real clicks/typing with CGEvent instead.

## Architecture

Single module, `Sources/Vestitel/`. Everything runs on the main actor.

- **`AppStore`** — the one `ObservableObject`, injected as `@EnvironmentObject` everywhere. Owns all state, timers, fetching, persistence, and every user action. Views never mutate model data directly.
- **`Models.swift`** — plain Codable structs. `Article` moves through a state machine: inbox (unread → read via `readAt`) → cleared (`clearedAt`) → purged. Time-based transitions happen in `AppStore.sweep()` (30 s timer): read articles clear after 15 min, cleared articles purge after 24 h. A `seen` id→date map (30-day retention) prevents purged articles from re-ingesting.
- **`StorePageParser`** — regex HTML scraper for store product-listing pages (ozone.bg-style `product-box` cards), producing the same `ParsedFeed` shape as RSS. Feeds with `kind == .store` use it; `addFeed` falls back to it when RSS parsing fails. Store articles live in a separate Store tab (`store.storeInbox`, excluded from `inbox`/grouping), are never capped by `maxArticlesPerFeed`, and their `seen` entries are exempt from the 30-day pruning in `sweep()` — that permanence is the whole point: a cleared product must never re-ingest. Products are scoped to the result grid (`id="products-list"`): the same `product-box` markup is also used by recommendation carousels above it, which are not listing results. `parseListing` additionally returns the pager's page count (`?p=N` links, highest wins; 1 when unpaginated) for `StoreScan`.
- **`StoreScanner`** — the ozone.bg "latest additions" watch, and a deliberately separate subsystem from store-watch feeds. That page doesn't order products by when they appeared (a product added today can sit ten pages deep), so the scan walks *every* page of `StoreScan.listingURL` sequentially, pausing 4–9 s between requests: dozens of requests to one host must not look worth blocking, and a full pass takes ~5 min. At that length a single flaky request is likely (a live 47-page pass timed out on page 44), so each page retries twice with a longer backoff — but never on a `FeedBlockedError`, where backing off harder doesn't help and re-requesting is exactly wrong. Results never enter the inbox (a listing holds thousands of products) — they're diffed against `storeScanSeen` (product URL → first seen) and rendered by `StoreScanReport` into a throwaway HTML page in the temp directory, regenerated on demand rather than kept. The first pass is a *baseline*: it reports nothing and only records what's listed, and `storeScanBaselineDone` flips only when a walk completes, so a half-finished baseline can't make the listing's whole tail look new next time. Likewise only a complete walk may prune `storeScanSeen` — after a partial scan the unvisited pages' products would look gone and re-report. Pruning keeps anything still listed regardless of age. The daily 08:30 run is checked from `sweep()` (every 30 s) rather than a one-shot timer, which sleep, a late launch or a clock change would silently miss; `lastStoreScanAttempt` is stamped *before* the first request so a failing scan can't retry every 30 s all day. Scan state is per-machine — it is not part of the sync document.
- **`LocalSources`**: the ingress for other apps and scripts on this Mac ("things that happened"). Two transports, one model: a drop folder (`Application Support/Vestitel/Events/`, under `VESTITEL_STATE_DIR` for test instances) where a producer writes a JSON file holding one event or an array (`source` + `title` required; `url`, `summary`, `image`, `published`, `id` optional), and the `vestitel://add?source=…&title=…` URL scheme (`CFBundleURLTypes` in Info.plist, received by `AppDelegate.application(_:open:)`). Files are consumed on launch, on every `refreshAll`, and within ~1 s via a `FolderWatcher`; unparseable ones move to `Events/Rejected/` so they are visible but never retried. Each `source` maps to a `Feed` of kind `.local` with the deterministic URL `vestitel://source/<slug>`; that URL is only an identity (article ids, sync matching by URL, colour), never fetched: `refreshAll`/`refreshFeed` skip local feeds, the row has no refresh button, and `Feed.faviconHost` is nil so no favicon lookup hits the fake host. Events go through the ordinary `ingest` (uncapped, like store feeds), so the inbox hold, grouping, sync and the read/cleared/seen machine all apply unchanged. A removed source is recreated when its producer posts again (the tombstone is cleared, as in `addFeed`). URLs are buffered in `OpenURLQueue` because when the app is *launched* by a URL the delegate callback and `AppStore` creation race. To test the scheme, `open "vestitel://add?…"` goes to the running instance of the registered bundle, so with the real app quit it reaches a `VESTITEL_STATE_DIR` instance started from the same `Vestitel.app`; `lsregister -f Vestitel.app` after changing Info.plist.
- **`FeedParser`** — dependency-free RSS 2.0/1.0/Atom parser on `XMLParser`. Namespace prefixes are stripped to local names, so `media:content` arrives as `"content"` (shared case with Atom's `<content>`, disambiguated by the `url` attribute).
- **`TopicGrouper`** — clusters same-story articles across sources: union-find over pairwise links from keyword-Jaccard (language-agnostic) OR NL sentence embeddings gated on ≥2 shared-token weight AND on `NLLanguageRecognizer` saying the title is English — the English model maps text it can't represent (Cyrillic!) to near-identical vectors, so ungated it links any two Bulgarian titles as "semantically the same". Tokens drop <3-char words, numbers, and a bilingual (English + Bulgarian) stopword list of function words and news-rubric noise ("видео", "снимки", "млн", "breaking"…); hyphenated compounds stay whole ("22-годишна", "Е-79"); Bulgarian definite-article suffixes are stripped with vowel/consonant context guards (`normalize`: "детската"→"детска", "градът"→"град", but "злато"/"карта"/"краят" untouched), and stopwords are checked in both raw and normalized form. Text inside quotes („…“, “…”, «…», "…") becomes a single phrase token, counted double in the shared-token shortcut — a shared quoted name is a strong same-story signal. Multi-word named entities ("South Korea", via `NLTagger` nameType, English-only) are the opposite: the joined phrase token absorbs its component words in the weighting so a shared name counts once, and the components stay in the set so "Trump" still matches "Donald Trump". A pair needs shared weight ≥ 2 to link at all — one shared word or name is never the same story. Embeddings are expensive: vectors are memoized per title here, and the resulting group *structure* (ids, not Article values) is cached in `AppStore.groupCache`, invalidated by inbox-composition/sensitivity changes and warmed right after ingest. Don't call `TopicGrouper.group` from view code — go through `store.groupedInbox`.
- **`NotificationManager`** — local notifications (UserNotifications). Two cases. (1) A feed fetch answered with a bot-challenge page (`AppStore.looksBlocked`: `cf-mitigated` header, or 401/403/429/503 + HTML body) sets a readable `lastError` and posts a notification with an "Open Website" action; once per block episode per feed (`notifiedBlockedFeeds`, in-memory), identifier keyed by host so repeats replace. (2) A finished listing scan posts an "Open Report" notification (identifier `store-scan`, so a later scan replaces it) — always, since "nothing new today" is a result too. Its action carries no file path: it calls `onOpenStoreScanReport` (wired to `AppStore.openStoreScanReport` in `init`), which re-renders the report, so it still works after the temp file is swept away or the app restarted. The response handler branches on `categoryIdentifier`. Authorization is requested lazily on first use. Banners aren't AX-clickable — verify delivery via `log show --predicate 'process == "usernoted"'`.
- **`MenuBarIcon`** — pre-rendered NSImage variants of the mascot (monochrome template / coloured / head-only-coloured × eyes-up / eyes-down-tilted, plus 16 animation frames × 2). State priority lives in `VestitelApp.menuBarLabel`: animation > colour signals (if `allowColoredIcon`) > monochrome; eyes-down whenever the inbox is non-empty. Monochrome variants are true template images (eyes/mouth are alpha punch-outs); partially-coloured variants can't be templates, so their waves use fixed mid-gray.
- **`SyncEngine`** — optional multi-Mac sync through any shared folder (Google Drive etc., set via `settings.syncFolderPath`). Each machine writes only its own `vestitel-<machineID>.json` and merges the others' on launch, after every refresh, on popover open, and whenever a `FolderWatcher` (FSEvents on the sync folder, 2 s coalescing, `IgnoreSelf` so our own writes don't re-trigger; the same class watches the local events folder) sees another machine's file change — no file has two writers, so the transport can't conflict. Merge rules: unions everywhere; `seen` keeps the earliest date (never-show-again propagates); cleared beats inbox (restore loses across machines by design); deletions travel as tombstones (`removedFeeds`/`removedBookmarks`/`archiveClearedAt`) because absence is not a signal; remote feed ids are remapped to local ones by URL; a locally-seen id with no local article means "already purged here" and is never re-adopted. Settings stay per-machine. In `load()`, `settings` must be assigned last — its `didSet` fires `save()` → `writeSyncDocument()`, which must see the loaded `machineID`.
- **`SourcePalette`** — per-feed colours. Automatic assignment must stay deterministic for the same *set* of feed URLs: FNV-1a hash (Swift's `Hasher` is seeded per launch — never use it for anything persisted/displayed-stable) + CIELAB ΔE-aware slot probing in URL-sorted order. Manual `colorIndex` overrides always win.
- **`Views/`** — `ContentView` (header + tab switch + shared row components), `InboxView` (groups), `StoreView` (store inbox + `StoreScanCard`), `ClearedView` (also hosts Archive views), `BookmarksView`, `SettingsView`. The Store tab appears when `store.showsStoreTab` — a store-watch feed *or* the latest-additions scan being on. `Tools/make-icon.swift` draws the app icon; keep it visually in sync with `MenuBarIcon`.

## Hard-won constraints (violating these reintroduces fixed bugs)

- **Swipe gestures**: `DragGesture` on a view that moves with its own offset MUST use `coordinateSpace: .global`; local space feeds the offset back into the translation and oscillates. Row/group swipe uses the "drop target" pattern: fixed-size pane at the destination edge, layered *above* the row, armed at 75% of `actionWidth`, commit on release while armed. The row gets an opaque `windowBackgroundColor` background while dragging so the pane never shows through. Clicks are detected inside the gesture (`dragIsHorizontal == nil` on end), not via `onTapGesture`.
- **Row layout is hover-invariant**: action buttons never appear/disappear in ways that reflow text — they fade via `opacity` with `allowsHitTesting` gated (`RowActionButton.visible`), or are always visible (`InlineActionButton` bar). The per-article clear × stays top-right regardless of card height.
- **Codable evolution**: every new persisted field must decode tolerantly — optional field, or `decodeIfPresent` with default in a custom `init(from:)` (`AppSettings` already has one; `PersistedState` uses optionals). A decode failure silently loses the user's entire state.
- **No ticking timestamps** in the UI: use `Date.articleDisplay` (absolute, time-only for today), never `Text(_, style: .relative)`.
- Articles ingested without a publish date get `published = fetch time` by design (displayed as "when it was added").
- `MenuBarExtra` label updates are driven by `@Published` changes on the store; the popover's `onAppear`/`onDisappear` set `popoverOpen` and acknowledge `hasUnseenArticles` — that's the only "is the app open" signal available.
- **Inbox hold**: while the popover is open on the Inbox tab, arriving articles (fetch or sync merge) are hidden behind `inboxHoldStart` (a fetchedAt cutoff, in-memory only) so the list never shifts mid-read; a "N new" header button moves the cutoff forward, closing the popover or leaving the tab drops it. Anything that adds inbox articles must give them `fetchedAt = now` (sync adoption does this deliberately), and anything operating on "all inbox articles" must skip held ones (`clearInbox` does — never clear what was never shown).
- The whole-row tap on Settings toggle rows (`SettingRow.onTap`) is intentional; keep it when adding toggles, skip it for pickers.
